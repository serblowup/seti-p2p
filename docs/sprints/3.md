# Спринт 3. Подписанные записи DHT, STORE / FIND_VALUE, репликация

**Этап:** 3 (недели 5–6).
**Контрольный результат:** подписанная запись находится после отказа
одного хранителя.
**Уровень:** продвинутый (все обязательные, желательные и опциональные
требования этапа 3, `N = 20`, `K = 4`, `R = 3`).

## 4. Репликация `R = 3`

Семантика после доработки Е3-4: реплики — **три ближайших по XOR**
узла из `Lookup`, включая владельца, **если он попал в тройку**.
Локальная копия владельца ведётся отдельно и **не** считается репликой,
если владелец не в тройке.

| ID | Требование | Где реализовано |
|---|---|---|
| REP-1 | `R = 3` хранителей — три ближайших по XOR из `Lookup` | `internal/node/dht_ops.go`: `ReplicationFactor = 3`, `selectReplicasByXOR(lookupRes.Closest, R)` |
| REP-2 | Локальная копия владельца ведётся отдельно | `Put`: `localErr := n.store.Put(rec)`; `res.LocalStored = (localErr == nil)`. Локальная копия **не** входит в `Acks`/`Replicas`, если владелец не в тройке |
| REP-3 | Владелец входит в `Acks`/`Replicas` только если он в тройке | `Put`: цикл по `replicas`; для `self` `Acks++` только если `localErr == nil`; `StoredAt += self` |
| REP-4 | Успех при `acks >= 2` среди трёх ближайших | `StoreAckThreshold = 2`, `res.Success = res.Acks >= StoreAckThreshold` |
| REP-5 | Журнал выбора хранителей | `store put key=… replicas=… acks=… success=… local_stored=… duration=…ms stored_at=…` |
| REP-6 | `stored_at` содержит подтвердивших | `stored_at=<shortID1>,<shortID2>,…` — только те, кто вернул `Stored=true` (и владелец, если он в тройке и локальный `Put` прошёл) |
| REP-7 | Тесты на репликацию | `TestPutThenGetAcrossNodes`, `TestGetAfterReplicaFailure`, `TestPutReplicasByXOR`, `TestPutOwnerLocalEvenIfNotInReplicaSet` |
| REP-8 | Работа на `N = 20, K = 4` | `scripts/store_experiment.sh`: `replicas=3 acks=3` в логах, `stored_at` из трёх `shortID` |
| REP-9 | Владелец не в тройке — `LocalStored=true`, `StoredAt` без владельца | `TestPutOwnerLocalEvenIfNotInReplicaSet` (лог: `owner in replica set: false (storedAt=3 replicas=3 acks=3 N=20 K=4)`) |
| REP-10 | `republish` не зависит от кворума | `republishOnce` вызывает `Put`; локальная копия обновляется через `LocalStored` даже при `Success=false`. Покрыто `TestRepublishExtendsTTL`, `TestStopSavesFinalStoreState` |

**Семантика `StorePutResult`:**

- `Replicas` — число выбранных хранителей из тройки ближайших по XOR
  (до `R = 3`).
- `Acks` — число подтвердивших среди выбранных (`Stored=true`); если
  владелец в тройке и его локальный `Put` прошёл, он даёт одно
  подтверждение.`docs/sprints/3.md` целиком, с обновлениями под Е3-2, Е3-4, Е3-7 и свежие результаты `store_experiment.sh`.  
  

```markdown
- `LocalStored` — владелец положил запись локально (для `republish`
  и локального кэша); не входит в `Acks`/`Replicas`, если владелец не
  в тройке.
- `StoredAt` — контакты подтвердивших.

В логе `replicas=` = `Replicas`, `acks=` = `Acks`,
`local_stored=true/false` = `LocalStored`. Если владелец не в тройке,
`StoredAt` не содержит владельца, но `LocalStored=true` и запись у
владельца в `store`. Это используется `republishLoop` и `SaveToDisk`
в `Stop()`.

## 10. Эксперимент

### 10.1. `store_experiment.sh` на `N = 20, K = 4, R = 3`

```
NODES=20 K=4 ALPHA=3 SCHEME=<scheme> RUNS=50 KILL_REPLICA=1 ./scripts/store_experiment.sh
```

Скрипт:

1. Поднимает сеть `N = 20, K = 4`.
2. Каждый узел публикует свою запись через `-publish-self`.
3. Собирает ключи из логов.
4. При `KILL_REPLICA=1` находит в логе `store put` список подтвердивших (`stored_at`) и убивает **именно хранителя** (не владельца и не `node-01`). Жертва выбирается только среди ключей, у которых `stored_at` содержит ровно три `shortID` (`acks = 3`): после отказа остаётся хотя бы один живой удалённый хранитель.
5. Для каждого прогона поднимает reader-узел с `-get-key`, bootstrap через три первых узла (`9101, 9102, 9103`).
6. Собирает CSV: `run,initiator,target_key,is_victim_key,success,seq,rpcs,iters,duration_ms`.
7. Печатает в summary строку `victim_key=<short> reads=<N> success=<M>` — прямое подтверждение E3-5 из сырых данных.

### 10.2. Сводка по четырём схемам (`N = 20, K = 4, R = 3, KILL_REPLICA = 1, RUNS = 50`)

| Схема | Success | avg rpcs | avg iters | avg duration | median duration | `victim_key` reads / success | `non_victim` reads / success |
|---|---:|---:|---:|---:|---:|---|---|
| `star` | 49/50 | 7.02 | 2.49 | 1.20 ms | 1.00 ms | 27 / 27 (100%) | 23 / 22 (96%) |
| `ring` | 49/50 | 7.90 | 2.80 | 1.18 ms | 1.00 ms | 25 / 25 (100%) | 25 / 24 (96%) |
| `tree` | 50/50 | 7.12 | 2.56 | 1.12 ms | 1.00 ms | 26 / 26 (100%) | 24 / 24 (100%) |
| `multi-seed` | 39/50 | 7.95 | 2.74 | 1.41 ms | 2.00 ms | 25 / 15 (60%) | 25 / 24 (96%) |

Столбец `is_victim_key` в CSV (`1`, если `target_key == VICTIM_KEY`) позволяет автоматически подсчитать, сколько раз читался ключ убитого хранителя и сколько из этих чтений были успешными. В summary печатается строка `victim_key=<short> reads=<N> success=<M>`.

### 10.3. Интерпретация

- **E3-5 подтверждён на всех четырёх схемах.** После отказа хранителя ключ убитого хранителя читался и был успешно найден:
  - `star` — 27/27 (100%);
  - `ring` — 25/25 (100%);
  - `tree` — 26/26 (100%);
  - `multi-seed` — 15/25 (60%).

### 10.4. `TestRepublishExtendsTTL`

`TTL = 4 с`, `republishInterval = 2 с`. Через 5 секунд после `PutLocal` запись жива, `ExpiresAt` сдвинут вперёд, `SequenceNumber` увеличен. При `N=2` лог `republish` показывает `replicas=1 acks=1 success=false local_stored=true` — второй узел не попал в тройку ближайших по XOR, но `LocalStored=true`, `SequenceNumber` обновлён локально, TTL продлён. Тест занимает ~5.0 секунды, при `go test -short` пропускается.

### 10.5. `TestStopSavesFinalStoreState`

Узел с `TTL = 4 с`, `republishInterval = 2 с`. Через 3 секунды после `PutLocal` `republishOnce` срабатывает, `SequenceNumber` увеличивается. Затем `Stop()`: `cancel()` → `bgWG.Wait()` → `closeConns()` → `connWG.Wait()` → `SaveToDisk()`. После рестарта из того же `StateDir` `StoreGet` возвращает **последнюю** версию (`SequenceNumber` совпадает с той, что была после `republish`), а не ту, что была на момент входа в `Stop()`. При `N=1` лог `republish` показывает `replicas=0 acks=0 success=false local_stored=true` — тройка пуста, но `LocalStored=true` и снимок содержит новую версию.

### 10.6. Псевдонимы

- `PutAlias` / `GetAlias` на `N = 20`: `alice` → `ALICE` → `alice`, `source=remote`, `node=c1`.
- `TestAliasLastWriterWins` подтверждает локальный last-writer-wins на стороне хранителя: `sequence_number` 1 → 2 вытесняет предыдущую версию, `GetAlias` возвращает `c2` (`source=remote`), а не устаревшую локальную копию `seed` от `c1`.
- `PutAlias` отклоняет чужую запись (`ErrAliasNotOwn`), запись с уже установленным `alias` (`ErrAliasAlreadySet`) и запись, не прошедшую `Validate` (`alias: invalid record: …`).

## 14. Итог спринта 3

Все обязательные, желательные и опциональные требования этапа 3
выполнены на продвинутом уровне:

- E3-1 … E3-6 (обязательные) — реализованы и протестированы;
- E3-7 (желательное) — `republishLoop` с интервалом `TTL/2`,
  `expireLoop` с очисткой TTL, `Stop()` дожидается `bgWG` перед
  `SaveToDisk()`; `TestRepublishExtendsTTL`, `TestStopSavesFinalStoreState`;
- E3-8 (опциональное) — псевдонимы с нормализацией, детерминированным
  ключом, тестами конкурирующих версий.

Дополнительно выполнены требования продвинутого уровня из ТЗ:

- `N = 20`, `K = 4`;
- `R = 3` — три ближайших по XOR хранителя, включая владельца только
  если он в тройке; `StoreAckThreshold = 2`;
- локальная копия владельца ведётся отдельно (`LocalStored`), не
  входит в `Replicas`/`Acks`/`StoredAt`, если владелец не в тройке;
- `republish` не зависит от кворума: `Put` кладёт запись локально
  первым, `cloneForRepublish` обновляет `SequenceNumber` локально;
- `FIND_VALUE` добирает до `k` ближайших и возвращает версию с
  наибольшим `sequence_number`, прошедшую `Validate(now, nil)`;
- `node.Get` всегда идёт в `FindValue` (если `TableSize() > 0`),
  локальная устаревшая копия не перекрывает удалённую;
- `handleFindValue` повторно вызывает `Validate(now, nil)` перед
  возвратом записи — защита в глубину;
- `netutil.ValidateHostPort` поддерживает IPv4, IPv6 (в скобках) и
  RFC 1123 hostname;
- `TestPutReplicasByXOR`, `TestPutOwnerLocalEvenIfNotInReplicaSet`,
  `TestFindValueRejectsExpiredRemoteRecord`,
  `TestFindValueDropsInvalidStoredRecord`,
  `TestGetRejectsExpiredRemoteRecord`, `TestStopSavesFinalStoreState`,
  `TestBootstrapAndLookup/advanced_N20_K4` — подтверждают
  семантику на продвинутом уровне.

**Ограничения модели, зафиксированные в отчёте:**

- глобальной согласованности нет: локальный last-writer-wins по
  `sequence_number` на каждом хранителе;
- нет anti-entropy: если `Put` не дошёл до хранителя, он не «догонит»;
- нет защиты от захвата псевдонимов: любой узел может опубликовать
  запись по любому ключу `SHA-256("alias:" || x)`;
- нет TLS/AKE: публичный ключ передаётся в открытом виде;

**Контрольный результат этапа 3 достигнут:** подписанная запись
находится после отказа одного из трёх хранителей. На `N = 20, K = 4,
RUNS = 50` `store_experiment.sh` показал:

- `49/50` на `star` (victim 27/27, 100%);
- `49/50` на `ring` (victim 25/25, 100%);
- `50/50` на `tree` (victim 26/26, 100%);
- `39/50` на `multi-seed` (victim 15/25, 60%).

Во всех схемах ключ убитого хранителя был успешно прочитан хотя бы
раз.
