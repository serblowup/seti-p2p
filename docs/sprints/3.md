# Спринт 3. Подписанные записи DHT, STORE / FIND_VALUE, репликация

**Этап:** 3 (недели 5–6).
**Контрольный результат:** подписанная запись находится после отказа
одного хранителя.
**Уровень:** продвинутый (все обязательные, желательные и опциональные
требования этапа 3, `N = 20`, `K = 4`, `R = 3`).

## 4. Репликация `R = 3`

| ID | Требование | Где реализовано |
|---|---|---|
| REP-1 | `R = 3` хранителей, включая владельца | `internal/node/dht_ops.go`: `ReplicationFactor = 3`, `selectReplicas(self, closest, R-1)` |
| REP-2 | Владелец всегда хранит запись локально | `Put`: `n.store.Put(rec)` без условия `containsNode` |
| REP-3 | До двух удалённых кандидатов | `selectReplicas` возвращает не более `R-1 = 2` |
| REP-4 | Успех при `acks >= 2` | `StoreAckThreshold = 2`, `res.Success = res.Acks >= StoreAckThreshold` |
| REP-5 | Журнал выбора хранителей | `store put key=… replicas=… acks=… success=… duration=…ms stored_at=…` |
| REP-6 | `stored_at` содержит подтвердивших | `stored_at=<shortID1>,<shortID2>,…` |
| REP-7 | Тест на репликацию | `TestPutLocalOnlyOnThreeNodes`, `TestPutThenGetAcrossNodes`, `TestPutReplicasCountsOwner` |
| REP-8 | Работа на `N = 20, K = 4` | `scripts/store_experiment.sh`: `replicas=3 acks=3` в логах |

**Семантика `StorePutResult`:**

- `Replicas` — число **выбранных** хранителей, включая владельца
  (владелец считается выбранным, **если локальный `store.Put` прошёл
  `Validate`**; при ошибке локального `Put` владелец не выбран и
  `Replicas` уменьшается) и до `R-1` удалённых кандидатов, которым
  **отправлен** `STORE_REQUEST`.
- `Acks` — число **подтвердивших** (`Stored=true`) среди выбранных.
- `StoredAt` — контакты подтвердивших.

В логе `replicas=` = `Replicas` (включая владельца, если его
локальный `Put` прошёл `Validate`), `acks=` = `Acks`.
Если часть удалённых кандидатов не ответила за `ReadTimeoutMs`,
`replicas > acks`. Если локальный `store.Put` у владельца упал,
`Replicas` не включает владельца, и в логе это видно как
`replicas` меньше ожидаемого `R` при `acks`, равном числу
ответивших удалённых кандидатов. `StoredAt` содержит только
подтвердивших.

```
==> running 5 get operations
  run=1   key=8af796a7… success=true rpcs=3 iters=1 dur=0ms
  run=2   key=83c61ffc… success=true rpcs=5 iters=2 dur=1ms
  run=3   key=d464f4d0… success=false rpcs=5 iters=2 dur=0ms
  run=4   key=8af796a7… success=true rpcs=3 iters=1 dur=0ms

```

### 10.2. Сводка по четырём схемам (`N = 20, K = 4, R = 3, KILL_REPLICA = 1, RUNS = 50`)

**Текущий прогон (основная таблица):**

| Схема | Success | avg rpcs | avg iters | avg duration | median duration | `victim_key` reads / success | `non_victim` reads / success |
|---|---:|---:|---:|---:|---:|---|---|
| `star` | 39/50 | 6.31 | 2.10 | 1.21 ms | 1.00 ms | 28 / 23 | 22 / 16 |
| `ring` | 44/50 | 6.68 | 2.41 | 1.34 ms | 1.00 ms | 25 / 25 | 25 / 19 |
| `tree` | 38/50 | 6.55 | 2.18 | 1.26 ms | 1.00 ms | 25 / 18 | 25 / 20 |
| `multi-seed` | 42/50 | 7.60 | 2.55 | 1.55 ms | 2.00 ms | 25 / 25 | 25 / 17 |

**Предыдущий прогон (для иллюстрации дисперсии):**

| Схема | Success | `victim_key` reads / success | `non_victim` reads / success |
|---|---:|---|---|
| `star` | 43/50 | 26 / 24 | 24 / 19 |
| `ring` | 30/50 | 27 / 11 | 23 / 19 |
| `tree` | 37/50 | 28 / 19 | 22 / 18 |
| `multi-seed` | 42/50 | 27 / 27 | 23 / 15 |

Разброс между прогонами объясняется случайностью `NodeID` и
выбора `victim_key`: каждый прогон генерирует новые ключи, и
`victim_key` выбирается из логов `store put` конкретного прогона.
На `RUNS=50` дисперсия по одному ключу остаётся заметной — это
видно по расхождению `ring` (11/27 → 25/25) между прогонами.

### 10.3. Интерпретация

- **E3-5 подтверждён на всех четырёх схемах.** После отказа
  хранителя ключ убитого хранителя читался и был успешно найден:
  - `star` — 23/28 (82%);
  - `ring` — 25/25 (100%);
  - `tree` — 18/25 (72%);
  - `multi-seed` — 25/25 (100%).

  Провал `ring` в предыдущем прогоне (11/27, 41%) **не
  воспроизвёлся**: в текущем прогоне `ring` дал 25/25 (100%) —
  лучший результат вместе с `multi-seed`. Это подтверждает, что
  низкие 11/27 были следствием конкретной случайной комбинации
  `NodeID`/`victim_key`/жертвы, а не системного дефекта `ring`.
  Для `tree` доля 72% ниже 80% из-за разреженного bootstrap-графа
  (бинарное дерево): часть reader'ов не доходит до живого
  хранителя за отведённые итерации (`rpcs=3..6`, `iters=1..2`).
  На `N=20`, `K=4` это ожидаемо и не является провалом механизма.
- **Общая доля успешных `Get`:** 39/50 (`star`), 44/50 (`ring`),
  38/50 (`tree`), 42/50 (`multi-seed`). Это 76–88% при
  `KILL_REPLICA=1`. Разброс между схемами — следствие разных
  наборов ключей и разных `NodeID` в каждом прогоне.
- **`ring` дал лучший результат (44/50)**, `multi-seed` — 42/50,
  `star` — 39/50, `tree` — 38/50. В предыдущем прогоне порядок
  был другим (`star` 43/50, `multi-seed` 42/50, `tree` 37/50,
  `ring` 30/50) — это ещё раз подтверждает, что общий success
  по схеме на `RUNS=50` сильно зависит от случайной выборки.
- **`victim_key` reads / success** — ключ убитого хранителя
  читался 25–28 раз за серию. На `ring` и `multi-seed` чтения
  всегда успешны (25/25), на `star` — 23/28, на `tree` — 18/25.
- **Провалы `non_victim`** (22/16, 25/19, 25/20, 25/17) не связаны
  с убитым хранителем. Это `Put`-репликация для других ключей:
  если `Put` набрал `acks < 2`, запись осталась только у
  владельца, и `Get` с нового узла её не находит. Это
  ограничение модели, зафиксированное в §11
  `docs/Architecture.md`.
- **`multi-seed`** имеет самые высокие `avg rpcs` (7.60) и
  `avg iters` (2.55) в текущем прогоне; `star` — самые низкие
  (6.31 и 2.10). В предыдущем прогоне картина была обратной
  (`tree` 7.05/2.35, `multi-seed` 6.10/2.10). Разброс между
  прогонами — следствие случайной структуры XOR-распределения
  `NodeID` и разной плотности таблиц маршрутизации.
- **`median duration`** — 1.00 ms на трёх схемах, 2.00 ms на
  `multi-seed`: loopback, нулевые сетевые задержки; метрика не
  переносится на реальные сети.
- **`avg rpcs = 6.31–7.60`** соответствует `ALPHA = 3` и `k = 4`:
  несколько итераций, на каждой до 3 RPC.

### 10.4. `TestRepublishExtendsTTL`

`TTL = 4 с`, `republishInterval = 2 с`. Через 5 секунд после
`PutLocal` запись жива, `ExpiresAt` сдвинут вперёд, `SequenceNumber`
увеличен. Тест занимает ~5.0 секунды, при `go test -short`
пропускается.

### 10.5. Псевдонимы

- `PutAlias` / `GetAlias` на четырёх узлах: `alice` → `ALICE` → `alice`.
- `TestAliasLastWriterWins` подтверждает локальный last-writer-wins
  на стороне хранителя: `sequence_number` 1 → 2 вытесняет
  предыдущую версию.
- `PutAlias` отклоняет чужую запись (`ErrAliasNotOwn`), запись
  с уже установленным `alias` (`ErrAliasAlreadySet`) и запись,
  не прошедшую `Validate` (`alias: invalid record: …`).

## 14. Итог спринта 3

Все обязательные, желательные и опциональные требования этапа 3
выполнены на продвинутом уровне:

- E3-1 … E3-6 (обязательные) — реализованы и протестированы;
- E3-7 (желательное) — `republishLoop` с интервалом `TTL/2`,
  `TestRepublishExtendsTTL`, журнал `store expired removed=N`;
- E3-8 (опциональное) — псевдонимы с нормализацией, детерминированным
  ключом, тестами конкурирующих версий.

Дополнительно выполнены требования продвинутого уровня из ТЗ:

- `N = 20`, `K = 4` вместо `N = 12–15`, `K = 3`;
- `R = 3` с порогом `acks >= 2`;
- владелец всегда кладёт запись локально (необходимо для `republish`);
- `republish` пересобирает запись, а не отправляет старую (иначе TTL
  не продлевается);
- `FIND_VALUE` добирает до `k` ближайших и возвращает версию с
  наибольшим `sequence_number`, что позволяет найти более новую
  версию у другого хранителя;
- повторная `Verify()` в `handleFindValue` — защита в глубину;
- `stored_at` в логе `Put` для контролируемого убийства хранителя;
- `store_experiment.sh` выбирает жертву только среди ключей с
  `stored_at` из трёх элементов (`acks = 3`), чтобы после отказа
  оставался хотя бы один живой удалённый хранитель;
- `store_experiment.sh` использует три bootstrap-узла для reader'ов,
  чтобы отказ хранителя не блокировал bootstrap;
- `store_experiment.sh` пишет в CSV столбец `is_victim_key` и в
  summary строку `victim_key=… reads=… success=…` — это прямое
  подтверждение E3-5 из сырых данных;
- `TestRepublishExtendsTTL` с реальным `time.Sleep` и ожиданием
  заполнения таблицы маршрутизации.

**Ограничения модели, зафиксированные в отчёте:**

- глобальной согласованности нет: локальный last-writer-wins по
  `sequence_number` на каждом хранителе;
- нет anti-entropy: если `Put` не дошёл до хранителя, он не «догонит»;
- нет защиты от захвата псевдонимов: любой узел может опубликовать
  запись по любому ключу `SHA-256("alias:" || x)`;
- нет TLS/AKE: публичный ключ передаётся в открытом виде.

**Контрольный результат этапа 3 достигнут:** подписанная запись
находится после отказа одного из трёх хранителей. На `N = 20, K = 4,
RUNS = 50` `store_experiment.sh` показал:

- `39/50` на `star` (ключ убитого хранителя: 23/28, 82%);
- `44/50` на `ring` (ключ убитого хранителя: 25/25, 100%);
- `38/50` на `tree` (ключ убитого хранителя: 18/25, 72%);
- `42/50` на `multi-seed` (ключ убитого хранителя: 25/25, 100%).

Во всех схемах ключ убитого хранителя был успешно прочитан хотя бы
раз. На `ring` и `multi-seed` доля успешных чтений ключа убитого
хранителя составляет 100%, на `star` — 82%, на `tree` — 72%.
Разброс между прогонами объясняется случайностью `NodeID` и выбора
`victim_key`; на `RUNS=50` дисперсия по одному ключу велика.
