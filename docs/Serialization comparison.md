# Сравнение форматов сериализации payload

**Документ:** обоснование выбора JSON для payload протокола на этапах 1–2.
**Источник данных:** `results/serialization-sizes.txt`, `results/serialization-bench.txt`.
**Воспроизведение:** `./scripts/bench.sh`.
**Окружение замера:** AMD Ryzen 5 7535HS, linux/amd64, Go 1.27.

---

## 1. Задача

Формат сериализации payload прикладного протокола должен:

- однозначно кодировать все поля сообщения;
- допускать строгую валидацию при декодировании (типы, обязательные поля);
- ограничивать размеры строк, массивов и вложенных структур;
- не использовать небезопасную десериализацию объектов;
- быть единообразным для всех узлов одной версии протокола;
- быть удобным для отладки на этапах 1–2.

По требованиям ТЗ этапов 1–2 (раздел 9) допускаются JSON,
MessagePack, CBOR, Protocol Buffers либо эквивалентный формат.
Требуется сравнить не менее двух альтернатив и обосновать выбор.

---

## 2. Сравниваемые форматы

| Формат | Тип | Схема | Стандарт |
|---|---|---|---|
| JSON | текстовый | не обязательна | RFC 8259 |
| MessagePack | бинарный | не обязательна | спецификация msgpack.org |
| CBOR | бинарный | не обязательна | RFC 8949 |

Все три формата — самоописывающие, схема не требуется. У нас нет
`.proto`, и каждый из форматов кодирует payload по структуре Go-типа.

---

## 3. Реализация

Основной протокол использует **JSON** через `internal/protocol/messages.go`:
`EncodePayload` / `DecodePing` / `DecodePong` / `DecodeFindNodeRequest` /
`DecodeFindNodeResponse` / `DecodeError`.

Альтернативные кодеки — `internal/protocol/altcodecs.go`:
`EncodeMsgpack` / `DecodeMsgpack` / `EncodeCBOR` / `DecodeCBOR`.
Они используются **только** в бенчмарке и не задействованы в рабочем
протоколе.

Замеры воспроизводятся скриптом `scripts/bench.sh` и сохраняются в
`results/serialization-sizes.txt` и `results/serialization-bench.txt`.

---

## 4. Размер payload

| Payload | JSON, байт | MessagePack, байт | CBOR, байт | msgpack, Δ | cbor, Δ |
|---|---:|---:|---:|---:|---:|
| PING | 245 | 184 | 189 | −24.9 % | −22.9 % |
| FIND_NODE_RESPONSE (k=3) | 914 | 688 | 706 | −24.7 % | −22.8 % |
| ERROR | 50 | 42 | 42 | −16.0 % | −16.0 % |

Бинарные форматы дают **экономию 16–25 %** относительно JSON на малых
payload за счёт отсутствия строковых ключей, кавычек и пробелов.
На больших структурах (`FIND_NODE_RESPONSE` с `k = 3`) экономия
стабильно держится около 23–25 %.

Для типичного `FIND_NODE_RESPONSE` с `k = 3` это означает экономию
**226 байт на кадр** у msgpack и **208 байт** у CBOR.

С ростом `k` до 4 (продвинутый уровень) абсолютная экономия
увеличивается пропорционально числу контактов в ответе.

---

## 5. Скорость encode

Медианы из трёх прогонов `go test -bench . -benchmem -count=3`.

| Операция | JSON, ns/op | MessagePack, ns/op | CBOR, ns/op |
|---|---:|---:|---:|
| Encode PING | 653 | 548 | **297** |
| Encode FIND_NODE_RESPONSE | 1719 | 1596 | **858** |

**CBOR выигрывает у JSON и msgpack по encode в 1.8–2.1 раза.** Это
следствие прямого кодирования в буфер без промежуточных
`map[string]interface{}`, которыми пользуется `encoding/json`.

Относительно JSON:

- msgpack быстрее по encode PING в **1.19 раза**, по FNR — в **1.08 раза**;
- CBOR быстрее по encode PING в **2.20 раза**, по FNR — в **2.00 раза**.

---

## 6. Скорость decode

| Операция | JSON, ns/op | MessagePack, ns/op | CBOR, ns/op |
|---|---:|---:|---:|
| Decode PING | 1060 | **635** | 765 |
| Decode FIND_NODE_RESPONSE | 3737 | **2325** | 2722 |

**MessagePack быстрее по decode** — в 1.4–1.7 раза относительно JSON и
в 1.2 раза относительно CBOR. Это объясняется оптимизированным
декодером `vmihailenco/msgpack/v5`, который читает бинарные поля
напрямую без разбора текстовых токенов.

Относительно JSON:

- msgpack быстрее по decode PING в **1.67 раза**, по FNR — в **1.61 раза**;
- CBOR быстрее по decode PING в **1.39 раза**, по FNR — в **1.37 раза**.

---

## 7. Аллокации

| Операция | JSON (B/op, allocs) | MessagePack (B/op, allocs) | CBOR (B/op, allocs) |
|---|---|---|---|
| Encode PING | 448, 3 | 592, 5 | **288, 2** |
| Decode PING | 176, 3 | 240, 6 | **192, 5** |
| Encode FNR | 1312, 3 | 2177, 7 | **912, 2** |
| Decode FNR | 1120, 13 | 1256, 24 | **872, 20** |

**CBOR аллоцирует меньше всего байт** (288 B и 912 B на encode).
При decode msgpack аллоцирует меньше байт, но делает больше вызовов
аллокатора (24 против 20 у CBOR). JSON по числу аллокаций формально
самый экономичный на PING (3 allocs), но с ростом размера payload
этот эффект пропадает: на FNR у JSON 13 allocs против 20 у CBOR.

Интересно, что msgpack при encode тратит **больше памяти, чем JSON**
(592 B против 448 B на PING): его энкодер использует внутренний буфер
и промежуточные аллокации. CBOR в этом смысле самый экономный.

## 8. Удобство валидации и отладки

| Критерий | JSON | MessagePack | CBOR |
|---|---|---|---|
| Читаемость в `tcpdump`/Wireshark | высокая | низкая | средняя (есть декодер) |
| Строгая валидация неизвестных полей | `DisallowUnknownFields` | нет встроенной | нет встроенной |
| Отклонение хвостовых данных | вручную через `dec.More()` | встроено | встроено |
| Ручное редактирование payload | тривиально | инструмент | инструмент |
| Совместимость с инструментами | максимальная | средняя | средняя |
| Пригодность для отладки в `grep`/`jq` | да | нет | нет |

JSON выигрывает по удобству отладки: payload можно открыть в редакторе,
посмотреть в `tcpdump`, воспроизвести вручную, отфильтровать в `jq`.
На этапах 1–2 это важнее, чем компактность: сообщений мало, они короткие.

---

## 9. Расширяемость

Все три формата самоописывающие: добавление нового поля не требует
изменения схемы. Различия:

- **JSON**: незнакомое поле при `DisallowUnknownFields` отклоняется,
  что позволяет ловить ошибки версионирования на раннем этапе.
- **MessagePack**: незнакомое поле игнорируется, если в структуре Go его нет;
  для строгости нужен кастомный `UnmarshalMsgpack` либо
  `msgpack.Decoder.DisallowUnknownFields()`.
- **CBOR**: аналогично msgpack, с опциональной строгостью через
  `cbor.DecOptions`.

Для этапов 1–2 строгость JSON — преимущество: она напрямую закрывает
требование «проверять типы и обязательность полей при декодировании»
и «не принимать неиспользуемые поля без документированного правила»
из раздела 9 ТЗ.

## 10. Вывод

**Для этапов 1–2 выбирается JSON.** Обоснование:

1. **Удобство отладки** в условиях, когда оверлей только разрабатывается:
   JSON-строки `lookup target=… rpcs=…` в журналах читаются глазами,
   payload воспроизводится вручную, `tcpdump` показывает читаемый текст.
2. **Строгая валидация «из коробки»**: `DisallowUnknownFields` + `dec.More()`
   дают полный контроль над схемой без сторонних библиотек.
3. **Нулевая зависимость от сторонних библиотек** — только
   `encoding/json` из stdlib. Это упрощает сборку и ревью.
4. **Экономия msgpack/CBOR на этом масштабе несущественна** для практики.
   Все payload малы (< 1 КБ). Узкое место — RPC-задержки и TCP-хендшейки,
   а не время encode/decode: медиана длительности lookup на loopback у нас
   составляет **1.00 мс**, а один encode PING — **0.65 мкс**, то есть
   **0.065 %** от времени операции. Даже двукратная разница в скорости
   кодирования на таком масштабе не наблюдаема.

**MessagePack или CBOR** становятся осмысленным выбором при переходе
к этапу 3 и далее, когда появятся:

- `STORE` / `FIND_VALUE` с подписанными `NodeRecord` размером порядка
  нескольких КБ;
- передача файлов блоками по 48–60 КиБ.

На этих объёмах 23–25 % экономии превращаются в реальные килобайты на
кадр, а CBOR по encode и аллокациям показывает лучший результат.
Решение принимается отдельно на этапе 3 по результатам экспериментов
и потребует bump версии протокола (`PROTOCOL_VERSION`).

Кодек изолирован в `internal/protocol/`: замена формата не затронет
транспорт, узел и DHT. Это оставляет пространство для смены формата
без переписывания базовой архитектуры.

## 11. Воспроизведение

```bash
./scripts/bench.sh
cat results/serialization-sizes.txt
cat results/serialization-bench.txt
```

Скрипт `scripts/bench.sh` выполняет:

1. `go test ./internal/protocol/ -run TestSerializationSizes -v` — размеры;
2. `go test ./internal/protocol/ -bench 'BenchmarkPing|BenchmarkFindNode' -benchmem -run '^$' -count=3` — скорости и аллокации.

Артефакты сохраняются в `results/`:

- `results/serialization-sizes.txt` — размеры payload;
- `results/serialization-bench.txt` — бенчмарки с тремя прогонами.
