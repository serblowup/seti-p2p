# Спецификация протокола seti-p2p

## 1. Назначение

Настоящий документ фиксирует формат кадра, набор типов сообщений, схемы
payload, правила формирования `NodeID`, устройство таблицы маршрутизации
Kademlia и алгоритм итеративного поиска узлов, реализованные в проекте
`seti-p2p` на этапах 1–2.

Документ является **спецификацией реализации**: любое расхождение между
этим текстом и кодом считается дефектом. Ссылки на модули даются явно:
`internal/protocol/frame.go`, `internal/protocol/messages.go` и т. д.

---

## 2. Термины

| Термин | Определение |
|---|---|
| **Узел** | Независимый логический экземпляр `bin/node` со своим `NodeID`, TCP-портом, каталогом состояния, таблицей маршрутизации и журналом |
| **Underlay-сеть** | Реальная IP-достижимость между процессами или контейнерами |
| **Bootstrap-узел** | Узел, чей адрес заранее известен новому участнику и используется только для первоначального входа в overlay |
| **DHT-overlay** | Логический граф контактов, хранящихся в таблицах маршрутизации узлов |
| **Контакт** | Проверяемая информация о другом узле: `NodeID`, публичный ключ, адрес и локальные метаданные наблюдения |
| **k-bucket** | Ограниченный по ёмкости список контактов заданного диапазона XOR-расстояний |
| **Lookup** | Итеративный поиск узлов, ближайших к целевому `NodeID`, через DHT RPC |
| **RPC** | Запрос прикладного протокола и соответствующий ему ответ, связанные полем `request_id` |

В общей loopback/Docker bridge-сети все узлы IP-достижимы друг для друга.
В этом случае схемы `star`, `ring`, `tree`, `multi-seed` являются
**схемами начального подключения**, а не физическими топологиями.

---

## 3. Транспорт

### 3.1. Основной транспорт

Основной транспорт — **TCP**. UDP в этапах 1–2 не используется.

Клиент использует **одно TCP-соединение на один RPC**: открывает
соединение, отправляет один кадр-запрос, дожидается одного кадра-ответа
и закрывает соединение. Это упрощает освобождение ресурсов и корреляцию
запроса и ответа, ценой дополнительного TCP-хендшейка на каждый RPC.
В loopback-экспериментах эта цена пренебрежимо мала.

**Сервер** читает кадры в цикле и способен обработать несколько RPC
в одном соединении (например, если клиент переиспользует соединение).
Текущий `RPCClient` этим не пользуется, но такая возможность заложена
в `handleConn` и пригодится на этапах 4–5, когда появится
долгоживущий защищённый канал.

Реализация: `internal/transport/conn.go`, `internal/transport/client.go`,
`internal/node/node.go` (`handleConn`).

### 3.2. Таймауты

Все таймауты задаются конфигурацией (см. §11) в миллисекундах:

| Параметр | Смысл | Значение по умолчанию |
|---|---|---:|
| `connect_timeout_ms` | установление TCP-соединения | 3000 |
| `read_timeout_ms` | ожидание кадра при RPC | 5000 |
| `ping_timeout_ms` | ожидание `PONG` | 5000 |

Каждое чтение кадра выполняется с `SetReadDeadline`; бесконечное
ожидание запрещено.

### 3.3. Ограничения

Реализация **не предполагает**, что один вызов `read()` возвращает
ровно один кадр, и **не предполагает**, что один `write()` соответствует
одному чтению у получателя. Для чтения используется `io.ReadFull` до
получения всего заголовка и всего payload.

## 4. Формат кадра

### 4.1. Заголовок

Все многобайтные целые числа кодируются в **сетевом порядке байтов**
(big-endian). Размер заголовка фиксирован: **24 байта**.

| Смещение | Поле | Размер | Тип | Описание |
|---:|---|---:|---|---|
| 0 | `version` | 1 байт | uint8 | Версия протокола. Для версии 1 — `0x01` |
| 1 | `type` | 1 байт | uint8 | Тип сообщения из §5 |
| 2 | `flags` | 2 байта | uint16 | Признаки. На этапах 1–2 всегда `0` |
| 4 | `request_id` | 16 байт | bytes | Идентификатор RPC; генерируется `crypto/rand` |
| 20 | `payload_length` | 4 байта | uint32 | Длина payload в байтах, от 0 до `MAX_FRAME_PAYLOAD` |
| 24 | `payload` | переменно | bytes | Сериализованные данные сообщения |

Реализация: `internal/protocol/frame.go`.

### 4.2. Ограничения

- `MAX_FRAME_PAYLOAD = 65536` байт (значение константы).
- Значение `payload_length` проверяется **до** выделения буфера под
  payload. При превышении `MAX_FRAME_PAYLOAD` кадр отклоняется с
  ошибкой, соединение закрывается.
- Значение `version` должно совпадать с `PROTOCOL_VERSION` узла.
  Иначе кадр отклоняется с `ErrBadVersion`.
- Поле `flags` на этапах 1–2 не интерпретируется; зарезервировано
  под признаки ответа, ошибки и фрагментации на будущих этапах.

### 4.3. Корреляция RPC

`request_id` генерируется на стороне инициатора криптографически
стойким генератором (`crypto/rand`). Ответ **обязан** содержать то же
значение `request_id`. Ответ с иным значением не принимается как ответ
на ожидающий запрос и приводит к ошибке `unexpected request_id in response`.

Реализация: `internal/protocol/codec.go`, `internal/transport/client.go`.

### 4.4. Обработка некорректных кадров

Узел закрывает входящее TCP-соединение после фиксации одного из нарушений:

- `version` не совпадает с ожидаемой;
- `payload_length > MAX_FRAME_PAYLOAD`;
- разрыв TCP до получения полного заголовка или payload;
- невозможность декодировать payload согласно схеме типа;
- `payload` не соответствует схеме указанного типа;
- запрос с типом, для которого нет обработчика.

**При возможности** узел перед закрытием отправляет `ERROR` с тем же
`request_id` (это реализовано в `handleConn`). Отправка `ERROR` не
производится, только если заголовок не может быть достоверно разобран
или соединение уже разорвано.

Код и сообщение ошибки не содержат стек вызовов, путей к файлам и
закрытых ключей.

## 5. Типы сообщений

| Код | Имя | Направление | Назначение |
|---:|---|---|---|
| `0x01` | `PING` | запрос | Проверка доступности и объявление контакта отправителя |
| `0x02` | `PONG` | ответ | Подтверждение доступности узла |
| `0x03` | `FIND_NODE_REQUEST` | запрос | Поиск контактов, ближайших к `target_node_id` |
| `0x04` | `FIND_NODE_RESPONSE` | ответ | Список ближайших известных контактов |
| `0x7F` | `ERROR` | ответ/уведомление | Ошибка протокола или обработки запроса |

Коды `0x05–0x3F` резервируются для следующих этапов: `STORE`,
`FIND_VALUE`, `TUNNEL_BUILD`, `TUNNEL_DATA`, `APP_MESSAGE` и т. д.
Изменение существующих кодов в версии 1 не допускается; введение новых
типов возможно без повышения версии, поскольку получатель обязан
отклонить неизвестный тип как ошибку протокола.

Реализация: `internal/protocol/frame.go`.

## 6. Сериализация payload

### 6.1. Формат

Payload сериализуется в **JSON** (RFC 8259) средствами стандартной
библиотеки `encoding/json`. Схема полей задаётся структурами Go и
тегами `json:"..."` в `internal/protocol/messages.go`.

Обоснование выбора JSON приведено в `docs/Serialization comparison.md`:
удобство отладки, строгая валидация через `DisallowUnknownFields` +
`dec.More()`, отсутствие внешних зависимостей. Сравнение с
MessagePack и CBOR выполнено в том же документе с числами.

### 6.2. Строгость декодирования

Все декодеры сообщений вызывают `decodeStrict`, который:

- отклоняет неизвестные поля (`DisallowUnknownFields`);
- отклоняет данные после закрытия JSON-объекта (`dec.More()`);
- отклоняет пустой payload.

Реализация: `internal/protocol/messages.go`, функция `decodeStrict`.

### 6.3. Схемы payload

#### 6.3.1. `PING`

```json
{
  "sender": {
    "node_id": "<hex/base64>",
    "identity_algorithm": "ed25519",
    "identity_public_key": "<DER SPKI>",
    "host": "127.0.0.1",
    "port": 9102
  },
  "timestamp_ms": 1730000000000
}
```

Поле `sender` — контакт отправителя; `timestamp_ms` — время отправки
в миллисекундах Unix.

#### 6.3.2. `PONG`

```json
{
  "responder": { ... },
  "ping_timestamp_ms": 1730000000000,
  "responder_timestamp_ms": 1730000000005
}
```

`ping_timestamp_ms` копируется из запроса; `responder_timestamp_ms` —
момент формирования ответа.

#### 6.3.3. `FIND_NODE_REQUEST`

```json
{
  "sender": { ... },
  "target_node_id": "<32 байта>"
}
```

`target_node_id` — 32 байта, проверяется на стороне получателя.

#### 6.3.4. `FIND_NODE_RESPONSE`

```json
{
  "responder": { ... },
  "target_node_id": "<32 байта>",
  "contacts": [ { ... }, { ... } ]
}
```

`target_node_id` копируется из запроса; `contacts` — не более
`k_bucket_size` уникальных контактов, отсортированных по возрастанию
XOR-расстояния до цели. Контакт отправителя и локальный контакт
исключаются.

#### 6.3.5. `ERROR`

```json
{
  "code": "handler_error",
  "message": "unsupported message type 0xfe"
}
```

`code` — короткая машиночитаемая метка класса ошибки. `message` —
человекочитаемое описание длиной не более 200 байт.

## 7. Идентичность узла

### 7.1. Долговременная пара ключей

Каждый узел при первом запуске создаёт долговременную пару
**Ed25519**. Закрытый ключ сохраняется в `state_dir` узла в формате
PEM (`PRIVATE KEY`), публичный — рядом (`PUBLIC KEY`).

Требования:

- закрытый ключ не передаётся по сети и не включается в образ контейнера;
- при повторном запуске из того же `state_dir` узел использует ту же пару;
- разные узлы в эксперименте используют разные пары.

Реализация: `internal/identity/identity.go`, функции `LoadOrCreate`,
`save`, `load`.

### 7.2. Вычисление `NodeID`

`NodeID` — 256-битный идентификатор:

```
NodeID = SHA-256(canonical_encode(identity_public_key))
```

`canonical_encode` — детерминированное представление публичного ключа.
В реализации используется **DER SubjectPublicKeyInfo**, то есть результат
`x509.MarshalPKIXPublicKey(pub)`.

Реализация: `internal/identity/identity.go`, функции
`CanonicalPublicKey`, `NodeIDFromPublicKey`, `VerifyNodeID`.

### 7.3. Проверка контакта

Полученный по сети контакт считается структурно допустимым только при
выполнении всех условий:

- `node_id` имеет длину 32 байта;
- `identity_algorithm` равен `"ed25519"`;
- `identity_public_key` корректно парсится как DER SPKI;
- `SHA-256(canonical_encode(public_key))` совпадает с `node_id`;
- `host` не пуст, `port` не равен нулю.

После проверки `FromWire` устанавливает `LastSeenMs = now`
(локальное время приёма). `LastVerifiedMs` остаётся нулевым до
первого успешного `PONG`.

Реализация: `internal/routing/contact.go`, функция `FromWire`.

### 7.4. Ограничения этапа 2

На этапах 1–2 криптографическая **аутентификация удалённой стороны не
выполняется**. Публичный ключ передаётся в составе `ContactWire` в
открытом виде, а MITM-атака не исключается. Защищённый канал
(TLS 1.3 с взаимной аутентификацией либо собственный AKE) — предмет
этапа 4. Это ограничение явно фиксируется в отчёте.

## 8. Контакт

### 8.1. Поля в сети

Контакт передаётся как `ContactWire` (`internal/protocol/messages.go`):

| Поле | Тип | Описание |
|---|---|---|
| `node_id` | `[]byte`, 32 байта | `NodeID` владельца |
| `identity_algorithm` | string | Всегда `"ed25519"` на этапах 1–2 |
| `identity_public_key` | `[]byte` | DER SPKI публичного ключа |
| `host` | string | Хост, по которому доступен узел |
| `port` | uint16 | TCP-порт |

### 8.2. Локальные поля

Внутренний контакт `routing.Contact` дополнительно содержит поля, которые
**не передаются по сети** и заполняются локально:

| Поле | Тип | Описание |
|---|---|---|
| `last_seen_ms` | uint64 | Локальное время последнего наблюдения контакта |
| `last_verified_ms` | uint64 | Локальное время последнего успешного `PONG` от контакта |

`LastSeenMs` устанавливается в `FromWire` в момент приёма контакта.
`LastVerifiedMs` обновляется в `node.observe` после успешного `PONG`
через `Contact.MarkVerified()` и `RoutingTable.TouchVerified`.

Узел **никогда** не доверяет значениям `last_seen_ms` из сети.

### 8.3. Дубликаты и конфликты

- Один `NodeID` присутствует в таблице маршрутизации не более одного раза.
- Контакт с тем же `NodeID`, но иным `identity_public_key`, отклоняется
  как нарушение идентичности.
- Контакт с тем же `NodeID` и иным `host:port` обновляется только после
  успешной проверки доступности.

## 9. XOR-метрика

### 9.1. Формула

Для двух 32-байтовых `NodeID` `a` и `b`:

```
xor_distance(a, b) = integer_from_big_endian(a XOR b)
```

Расстояние — беззнаковое 256-битное число. Сравнение — числовое
(`math/big.Int.Cmp`).

Реализация: `internal/routing/distance.go`, функция `XorDistance`.

### 9.2. Индекс bucket

Индекс bucket для контакта `c` относительно локального узла `l`:

```
idx = 256 - bit_length(xor_distance(l, c))
```

где `bit_length(0) = 0`. Тогда `idx ∈ [0, 255]`. Если `xor_distance = 0`,
контакт считается локальным и не добавляется в таблицу.

Реализация: `internal/routing/table.go`, функция `bucketIndexLocked`.

## 10. Таблица маршрутизации

### 10.1. Структура

Таблица маршрутизации (`RoutingTable`) состоит из **256 фиксированных
bucket** по индексу старшего установленного бита XOR-расстояния.
Каждый bucket имеет ёмкость `k_bucket_size` контактов.

Реализация: `internal/routing/table.go`, `internal/routing/bucket.go`.

### 10.2. Порядок контактов

Внутри bucket контакты упорядочены по времени последнего наблюдения:

- `contacts[0]` — наименее недавно подтверждённый (**LRU**);
- `contacts[n-1]` — самый свежий.

При вытеснении LRU-контакт удаляется через `copy` со сдвигом влево,
новый контакт записывается в освободившийся последний слот
(`Bucket.ReplaceLRU`). Это гарантирует отсутствие пересечения срезов
и сохраняет длину bucket.

### 10.3. Потокобезопасность

`RoutingTable` защищена `sync.Mutex`. Все публичные методы
(`Observe`, `Promote`, `ReplaceIfDead`, `TouchVerified`, `Nearest`,
`Snapshot`, `TotalContacts`) захватывают мьютекс на время работы.
Внутренняя реализация `observeLocked` используется внутри уже
захваченного мьютекса, чтобы избежать двойного захвата.

Это позволяет вызывать `Observe` из `node.observe` параллельно из
`handlePing`, `handleFindNode` и `node.Lookup` без гонок.

### 10.4. Операция `Observe`

При получении корректного кадра от удалённого узла либо корректного
`PONG` вызывается `node.observe`, которая вызывает `RoutingTable.Observe`:

1. Контакт проверяется по правилам §7.3.
2. Если контакт уже есть в bucket, он перемещается в конец (**Touch**).
3. Если контакта нет и bucket не заполнен — контакт добавляется в конец.
4. Если контакт отсутствует и bucket заполнен, `Observe` возвращает
   `checkLRU = true` и LRU-контакт. **Вызывающий код** (`node.observe`)
   обязан выполнить `PING` LRU-контакта:
   - при успешном `PONG` — `Promote(LRU)`, новый контакт не добавляется;
   - при тайм-ауте — `ReplaceIfDead(LRU, c)`, LRU-контакт вытесняется.

`node.observe` — **единственная точка** обновления таблицы. Модуль
`dht.Lookup` не имеет доступа к `RoutingTable` (см. §14.3).

Реализация: `internal/routing/table.go`, `internal/node/node.go`
(функция `observe`).

### 10.5. Правила, которые запрещены

- Вытеснение живого контакта без проверки только потому, что новый
  контакт имеет меньшее расстояние до локального узла.
- Добавление в таблицу двух контактов с одним и тем же `NodeID`.
- Добавление в таблицу контакта с локальным `NodeID`.

| `listen_port` | uint16 | — | TCP-порт узла |

| `k_bucket_size` | int | `3` | Ёмкость одного k-bucket |
| `alpha` | int | `3` | Параллелизм итеративного lookup |
| `connect_timeout_ms` | int | `3000` | Таймаут установления TCP |

| `ping_timeout_ms` | int | `5000` | Таймаут `PONG` |

правки кода.

Готовые конфигурации для экспериментов генерируются скриптами
`scripts/demo.sh` и `scripts/lookup.sh` в каталоге
`state-<scheme>/configs/`. Отдельного каталога `configs/` в
репозитории нет.

Реализация: `internal/config/config.go`.

## 12. Операция `PING`

### 12.1. Обработка запроса

Получив `PING`, узел обязан:

1. Декодировать payload строго (§6.2).
2. Проверить структуру контакта отправителя (§7.3).
3. Обработать контакт отправителя в таблице маршрутизации через
   `node.observe` (§10.4).
4. Сформировать `PONG` с тем же `request_id` и тем же `ping_timestamp_ms`.

### 12.2. Обработка ответа

Инициатор принимает `PONG` только при выполнении условий:

- `request_id` совпадает с ожидающим;
- ответ получен до `ping_timeout_ms`;
- контакт ответчика структурно корректен;
- если запрос адресован конкретному контакту — `node_id` ответчика
  совпадает с ожидаемым.

После успешного `PONG` контакт ответчика обновляется в таблице
маршрутизации, а `LastVerifiedMs` устанавливается в текущее время
через `RoutingTable.TouchVerified`.

Реализация: `internal/node/node.go`, функции `handlePing`,
`pingContact`, `Ping`.

## 13. Операция `FIND_NODE`

### 13.1. Обработка запроса

Получив `FIND_NODE_REQUEST`, узел обязан:

1. Декодировать payload строго.
2. Проверить длину `target_node_id` (ровно 32 байта).
3. Проверить структуру контакта отправителя.
4. Обработать контакт отправителя в таблице маршрутизации через
   `node.observe`.
5. Найти до `k_bucket_size` известных контактов, ближайших к
   `target_node_id` по XOR-метрике.
6. Исключить из ответа контакт отправителя и локальный контакт.
7. Отсортировать оставшиеся контакты по возрастанию расстояния.
8. Вернуть `FIND_NODE_RESPONSE` с тем же `request_id` и исходным
   `target_node_id`.

Ответ может быть пустым, если у узла нет подходящих контактов.
Отправка искусственно сгенерированных контактов, контактов из
центрального реестра или полного списка всех узлов запрещена.

Реализация: `internal/node/node.go`, функция `handleFindNode`.

### 13.2. Валидация ответа

Получив `FIND_NODE_RESPONSE`, инициатор обязан:

- проверить совпадение `request_id` и `target_node_id` с ожидающими;
- проверить структуру контакта ответчика и каждого возвращённого контакта;
- удалить дубликаты по `NodeID`;
- не добавлять локальный `NodeID` как удалённый;
- не доверять `last_seen_ms`, если оно вдруг пришло по сети;
- учитывать контакт ответчика как наблюдаемый только после корректного ответа.

## 14. Итеративный `FIND_NODE` lookup

### 14.1. Входные данные

```
lookup_node(target_node_id) -> LookupResult
```

`LookupResult` (`internal/dht/lookup.go`) содержит:

| Поле | Тип | Смысл |
|---|---|---|
| `target` | `[]byte` | Целевой `NodeID` |
| `success` | bool | `true`, если целевой `NodeID` найден |
| `closest` | `[]Contact` | До `k_bucket_size` ближайших контактов |
| `rpcs` | int | Число отправленных RPC |
| `iterations` | int | Число итераций |
| `timeouts` | int | Число таймаутов |
| `duration_ms` | int64 | Длительность в миллисекундах |
| `trace` | `[]IterationTrace` | Трассировка по итерациям |
| `discovered` | `[]Contact` | Валидные контакты, обнаруженные в ходе lookup. Не сериализуется в JSON (`json:"-"`). Используется `node.Lookup` для обновления `RoutingTable` через `node.observe`. |

`IterationTrace` содержит номер итерации, список опрошенных и список
обнаруженных контактов.

### 14.2. Алгоритм

Параллелизм `ALPHA` (`alpha` в конфигурации) определяет число
одновременных запросов на итерацию. По умолчанию `ALPHA = 3`.

1. Из таблицы маршрутизации выбираются до `k_bucket_size` ближайших
   к цели контактов — начальный набор кандидатов (`InitialCandidates`).
2. Кандидаты сортируются по возрастанию XOR-расстояния до цели.
3. На каждой итерации выбираются до `ALPHA` ещё неопрошенных кандидатов,
   ближайших к цели.
4. Выбранным кандидатам параллельно отправляются `FIND_NODE_REQUEST`.
5. Корректные ответы объединяются с текущим набором кандидатов;
   дубликаты удаляются по `NodeID`.
6. Контакты, завершившиеся тайм-аутом или ошибкой, фиксируются как
   `failed` и не опрашиваются повторно в этом lookup.
7. Поиск продолжается, пока существует хотя бы один неопрошенный
   кандидат, который ближе текущего `k`-го ближайшего.
8. Поиск завершается, когда дальнейший опрос не может улучшить список
   ближайших `k` контактов, либо когда пул неопрошенных кандидатов
   исчерпан.

Условие остановки (§14.2, п. 7) **не зависит** от того, найдена ли цель
в одном из ответов. Это принципиально для будущего `FIND_VALUE`: поиск
должен добирать до `k` ближайших хранителей, даже если значение уже
получено от одного из них.

### 14.3. Отсутствие доступа к `RoutingTable`

`dht.Lookup` **не имеет доступа** к `RoutingTable`. Он работает с
неизменяемым снимком `InitialCandidates`, взятым из таблицы до начала
lookup. Все обнаруженные контакты возвращаются в
`LookupResult.Discovered`, а вызывающая сторона (`node.Lookup`)
обрабатывает их через `node.observe` после `wg.Wait()`.

Это устраняет гонки при параллельных запросах внутри lookup и
сохраняет слоистость: `dht` не знает о `RoutingTable`.

### 14.4. Трассировка и логирование

Каждый lookup сопровождается записью в журнал:

```
lookup target=<hex> success=<bool> rpcs=<N> iters=<N> timeouts=<N> duration=<N>ms closest=<N>
  closest: <hex> @ <host>:<port>
  ...
```

Формат строки фиксирован. По нему работает парсер в `scripts/lookup.sh`,
который собирает CSV-серию экспериментов.

Реализация: `internal/dht/lookup.go`, `internal/node/lookup.go`,
`cmd/node/main.go`.

## 15. Bootstrap

### 15.1. Первый узел (seed)

Seed-узел запускается с пустым `bootstrap_peers`. Это **единственный
случай**, когда отсутствие bootstrap-контакта не является ошибкой
конфигурации. Его таблица маршрутизации изначально пуста.

### 15.2. Присоединение нового узла

Новый узел с непустым `bootstrap_peers` обязан выполнить:

1. Загрузку или создание identity-ключа и вычисление `NodeID`.
2. Установление TCP-соединения с хотя бы одним bootstrap-контактом.
3. `PING` bootstrap-узлу.
4. Добавление подтверждённого bootstrap-контакта в таблицу маршрутизации
   через `node.observe`.
5. Итеративный `FIND_NODE` для **собственного** `NodeID` (self-lookup).
6. Сохранение итогового состояния таблицы и журнала bootstrap-процесса.

После шага 5 bootstrap-узел **не требуется** для дальнейших lookup:
таблица заполнена и поиск идёт по ней.

### 15.3. Схемы начального подключения

Поддерживаются четыре схемы, задаваемые переменной `SCHEME` в
`scripts/demo.sh` и `scripts/lookup.sh`:

| Схема | Что знает узел `i` при старте |
|---|---|
| `star` | узел `i ≥ 2` знает только `node-01`; `node-01` не знает никого |
| `ring` | узел `i ≥ 2` знает только `node-{i-1}`; `node-01` не знает никого |
| `tree` | узел `i ≥ 2` знает только `node-{i/2}` (родитель в бинарном дереве) |
| `multi-seed` | seed-узлы `1..SEEDS` образуют цепочку; клиенты `i > SEEDS` знают два seed-узла (primary и secondary) |

Все схемы — **схемы начального подключения**, а не физические
топологии. В loopback-сети все узлы IP-достижимы друг для друга.

### 15.4. Особенности `multi-seed`

В `multi-seed` seed-узлы образуют цепочку: `node-02` знает `node-01`,
`node-03` знает `node-02` и т. д. Это создаёт связный граф seed-узлов.

Клиенты (`i > SEEDS`) подключаются к двум seed-узлам одновременно:

- primary: `seed_idx = (i - SEEDS - 1) % SEEDS + 1`
- secondary: `seed_idx = primary % SEEDS + 1`

Это создаёт перекрытие между разными «ветками» DHT. Без перекрытия
`multi-seed` фрагментируется на несколько независимых подграфов, и
DHT становится вырожденной.

### 15.5. Seed self-lookup

Seed-узлы выполняют self-lookup **после** того, как к ним подключился
хотя бы один клиент. Условие срабатывания в `cmd/node/main.go`:

```go
if len(cfg.BootstrapPeers) == 0 && nd.TableSize() > 0 {
    res, err := nd.Lookup(ctx, nd.NodeID())
    ...
}
```

Это позволяет seed-узлу обнаружить остальных через своего соседа и
заполнить таблицу контактами с разными XOR-расстояниями.

### 15.6. Отказ bootstrap-узла

После сходимости отключение bootstrap-узла не должно препятствовать
дальнейшим lookup между ранее присоединившимися узлами. Это проверяется
сценарием `SEED_FAILURE=1` в `scripts/demo.sh`: после успешного lookup
seed-узел убивается, и повторный lookup выполняется между двумя
другими узлами.

### 15.7. Проверка невырожденности

`scripts/check_non_degenerate.sh` проверяет три критерия:

1. Не менее 80% узлов имеют `contacts < N-1`.
2. Ни у одного узла нет полного каталога (`contacts >= N-1`).
3. Не менее 80% узлов имеют ≥2 непустых bucket.

Результат сохраняется в `results/<scheme>-nondegeneracy.json`.

Скрипт завершается с `exit 2`, если число initial-дампов не совпадает
с `NODES`: это исключает ложный PASS при неполном наборе данных.

## 16. Ограничения этапа 2

Следующие механизмы **не** реализованы на этапах 1–2 и не должны
считаться частью протокола версии 1 в текущем состоянии:

- `STORE` и `FIND_VALUE` — хранение подписанных `NodeRecord`;
- TTL записей, репликация, переопубликование;
- криптографическая аутентификация канала (TLS 1.3 с mutual auth либо
  собственный AKE);
- end-to-end шифрование прикладных данных;
- туннельная ретрансляция (`TUNNEL_BUILD`, `TUNNEL_DATA`, …);
- прикладные сообщения и передача файлов;
- защита от Sybil/Eclipse за пределами ограниченности k-bucket;
- анонимность относительно глобального наблюдателя.

Эти пункты — предмет этапов 3 и далее. Протокол версии 1 спроектирован
так, чтобы их добавление не требовало изменения формата кадра.
